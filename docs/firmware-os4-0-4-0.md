## OTA 后的模块迁移

旧模块在 OTA 换槽后可能仍记录原槽；旧卸载脚本也会因 Android 固件版本变化拒绝回退。本版在当前槽为新版原厂 Recovery 时接受跨槽升级，核对并保存旧模块的原厂镜像与安装记录，然后只写当前 Recovery。卸载按两个槽各自记录恢复。当前槽与原件不匹配、旧材料损坏或记录无效时拒绝安装；恢复时保留已被 OTA 或其他工具替换的分区。

回退不再要求当前 Android 版本等于安装固件。机型、解锁状态、分区大小、安装位置和完整镜像哈希仍须匹配。安装和模块操作入口继续严格要求 `OS4.0.4.0.XODCNXM`。

## 20261111.4 修复与补充验收

- 原厂振动 HAL 的 `on(timeoutMs)` 在本恢复环境中未自动停止。沿用原厂服务和波形，增加显式定时 `off`，替换请求不会被旧定时器提前终止，退出 GUI 时由 init 清理。真机 40 ms/160 ms 请求分别测得约 40.8 ms/161.0 ms，替换与空闲检查通过，反馈偏好不变。
- ORS 在关闭上一条命令的输出后，动作线程尚未退出；后续命令可能被拒绝且永久停在命令页面。现在等动作线程及原页面恢复完成后再结束客户端回复，监听恢复完成后才发送 EOF；仅对普通命令检查忙状态，保留界面内部的同步 xset 查询。连续 100 条命令回归通过。
- GUI 进程重启时，已有 metadata 映射的分支跳过了用户列表重建，fstab 末尾又无条件写回 `encrypted=1`。现在按同次启动的 CE 解锁记录重建用户状态；仅有 metadata 映射时仍初始化原 DE 流程并要求凭据。真机已解密会话在界面重启后恢复文件管理，自建 CE 文件读写与删除通过。
- KSU 模块页查询成功后不再把成功值改回待查询状态，失败分支只接受明确的失败结果；已完成进入、退出和重新进入三轮回归。
- ORS sideload 沿用 GUI 的 MTP 暂停与恢复流程，安装回调处理 ZIP 后不再进行第二次安装；完整退出流程单独记录真机结果。
- ORS 恢复开关与 OrangeFox 界面的“启用摘要检查”语义相反。正常恢复现在启用摘要校验，显式 `M` 才关闭；同时修正备份路径误译和缺失的恢复动作标题。
- KernelSU 卸载后正常重启 Android，A/B 的原厂 Recovery 均恢复为各自完整哈希，模块删除；28 份 GPT 原始文件逐字节一致，其余 36 个启动分区无变化，槽位仍为 A、BL 解锁。B 槽保持原有旧固件。
- 实际备份和恢复 Boot/Recovery，共 196 MiB，前后完整分区哈希一致。此项不等同于 userdata 的完整恢复验收。
- 通过 USB MTP 实际发送、读回并删除 1,075,000 字节自建文件，内容完全一致。

补充的 52 项检查执行真实 ARM64 控制流；用户枚举、属性、子进程及外部 DE 调用为测试桩。完整 userdata 恢复、ROM/OTA 和 OTG 未实测：不为验收清除个人数据，也不通过完整 OTA 覆盖原槽、GPT 或 UEFI。

### `.4` 当前候选的取消流程

- MTP 进程通过 fork 启动、不执行 exec，会继承 ORS 输出 FIFO；这使界面已完成时客户端仍收不到 EOF。配套修改主程序的唯一 forkserver 调用点和 MTP 库，仅在子进程关闭传入的 ORS fd。内存候选上实测 MTP 停止、启动后 CLI 分别在 0.050 秒和 0.066 秒返回，子进程已无 ORS 输出 fd。
- Disable_MTP 原本只提交 adb 请求就返回，sideload 可能读到旧 USB 状态，迟到的 adbd 启动也可能与 minadbd 重叠。现在等待本轮 adb 状态确认后继续，超时返回失败。
- sideload 的取消原本在界面线程执行 stat、sleep、waitpid，还提前设置 page_done。现在只在等待传输阶段解绑 USB 并通知子进程，后台线程负责回收与收尾；安装与取消互斥，开始安装后隐藏取消入口。
- sideload 在持久镜像 `33735267…` 上通过完整真实菜单：“高级 → ADB Sideload → 滑动开始 → 左上角 × → 返回”。后台动作结束、MTP/ADB 恢复并返回高级页，用户确认正常。随后通过相同入口发送仅绑定本次 Recovery 的 ZIP，实际将同一镜像写回 A 槽一次、完整读回、操作状态为 0，并返回高级页；没有用电脑端传输完成代替界面退出证据。
- 最终镜像 `1802648d…` 只进一步后移 fastbootd 的 USB 开放时点，保留上述取消、sideload、恢复和解密实现。冷启动时原代码在解析 `--fastboot` 时即开放 USB，主流程稍后才清理原启动请求，立即返回可能重进 fastbootd。现在沿用原有 BCB 清理，在 GUI 初始化和该清理完成后才开放 USB，不新增 BCB 写入或修改触摸驱动。真机在请求重启后约 18.498 秒首次出现 fastbootd；电脑于首次出现 0.077 秒后立即发送原生 reboot recovery，已成功回到新的 Recovery 启动，真实凭据解密、CE 文件读写和 KSU 模块页回归通过。
- 最终镜像通过 KSU 安装、完整分区回读及 Android 激活。正常返回 Android 后，自建 CE 文件完整读回并删除，28 份 GPT 原始文件逐字节一致；以磁盘 GUID 和容量匹配枚举名称。与双槽卸载后的基线相比，38 个启动相关分区仅 A 槽 Recovery 为本版镜像，B 槽原厂 Recovery 及其余 36 个分区一致；仍为 A 槽、BL 解锁，运行脚本与发布源码一致。
- 排查期间用户曾报告一次触摸无响应，失效时的输入事件未采集到；随后两次重新进入 Recovery 均获用户确认触摸正常。最终时序候选也已完成真实凭据输入和解密。该记录不作为已经定位并修复触摸驱动故障的结论。
